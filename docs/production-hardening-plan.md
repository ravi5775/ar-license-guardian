# Aether AR — Production Hardening and Ethical Operations Plan

**Status:** Planning document  
**Target:** 10/10 production readiness  
**Scope:** Build profiles, security, authentication, licensing, reliability, evidence, and ethical-use controls

## 1. Goals

The implementation is complete only when:

- all three build profiles are reproducible;
- authentication, authorization, tenant isolation, and licensing are enforced server-side;
- sensitive media and credentials cannot be accessed through permanent public URLs;
- security and performance claims have external evidence;
- abuse, privacy, and ethical-use controls are documented, reviewable, and auditable;
- production releases are reversible and require protected approval.

No score is marked `PASS` without an artifact produced by an external tool.

## 2. Delivery phases

### Phase A — Repository and release foundation

- Keep `main` as the canonical branch.
- Use build profiles instead of source-stripping branches:
  - `admin`
  - `client`
  - `selfhost`
- Pin Bun, Node, GitHub Actions, and security-tool versions.
- Remove stale branch and output-path references.
- Require pull-request checks before merging.
- Require protected environments for production deployment.

**Acceptance:** clean checkout builds all profiles with identical locked dependencies.

### Phase B — Build-profile architecture

- Centralize profile configuration in a typed module.
- Validate profile/environment combinations at startup and build time.
- Fail closed on contradictory values.
- Gate profile-sensitive routes and server functions, not only navigation.
- Assert the embedded profile in every generated artifact.
- Ensure client builds contain no issuer worker, signing key, or vendor-admin module.

**Acceptance:**

```text
bun run build:admin
bun run build:client
bun run build:selfhost
```

All succeed and profile isolation tests pass.

### Phase C — Authentication and authorization

- Use Supabase Auth with short-lived access tokens and rotating refresh tokens.
- Require verified MFA enrollment for every `owner` and `admin`.
- Require JWT `aal2` for every privileged mutation.
- Resolve the tenant only from the authenticated caller.
- Store roles only in `user_roles`.
- Protect role changes with an existing administrator and audit the change.
- Never trust client role flags, tenant IDs, or approval state.

**Acceptance:** negative tests prove that an AAL1 administrator, viewer, unauthenticated caller, and cross-tenant caller cannot perform privileged mutations.

## 3. Password hashing and credential handling

### Preferred algorithm: Argon2id

Use **Argon2id** for new password hashing where application-managed passwords are required.

Recommended starting parameters, subject to staging benchmarks:

```text
algorithm: Argon2id
memory: 64 MiB
iterations: 3
parallelism: 1 or 2
output: 32 bytes
salt: 16+ cryptographically random bytes
```

Parameters must be benchmarked on the production class of server and increased when latency and capacity allow. Store only the encoded password hash; never store plaintext passwords or reusable password material.

### Compatibility algorithm: bcrypt

Use **bcrypt** only for legacy hashes or compatibility with an existing identity store.

```text
cost: 12 minimum, benchmark before production
salt: generated by the library
```

On successful login with a legacy bcrypt hash:

1. verify the bcrypt hash;
2. issue the normal session;
3. rehash immediately with Argon2id;
4. replace the stored hash atomically;
5. audit the migration without recording the password.

Do not downgrade an Argon2id hash to bcrypt. Do not invent custom cryptographic formats. Use maintained, audited libraries and constant-time verification APIs.

### Credential controls

- Enforce password length and breached-password screening.
- Rate-limit sign-in by normalized email plus trusted ingress IP.
- Use generic login failure messages to prevent account enumeration.
- Revoke all sessions after password change or suspected compromise.
- Require step-up authentication for password, role, licence, and export operations.
- Keep service-role, R2, signing, mail, and worker secrets server-side only.
- Rotate credentials after any historical exposure.

## 4. Ethical-use and abuse-prevention architecture

“Ethical filtering” must be enforceable, explainable, privacy-preserving, and appealable. It must not silently profile people or make sensitive inferences.

### Allowed-use policy

Document permitted and prohibited uses, including:

- permitted event, marketing, educational, and portfolio experiences;
- prohibited harassment, stalking, impersonation, fraud, unlawful surveillance, non-consensual biometric use, and harmful content;
- customer responsibility for consent, copyright, privacy, and local law;
- an appeal and correction process;
- emergency suspension criteria with human review.

### Layered safeguards

1. **Input validation:** strict file type, size, magic-byte, metadata, and malware scanning.
2. **Content policy checks:** scan uploaded media and descriptions for prohibited content using a documented provider or self-hosted model.
3. **Consent controls:** require configurable consent notices for camera, analytics, location, and publication.
4. **Privacy minimization:** hash user agents, avoid unnecessary identity collection, and define retention periods.
5. **Abuse signals:** detect unusual activation, upload, scan, export, and login patterns without inferring protected characteristics.
6. **Human review:** route high-confidence abuse signals to an authorized reviewer; do not auto-ban solely on an opaque model score.
7. **Appeals:** preserve evidence, explain the decision category, allow correction, and record reviewer actions.
8. **Tenant isolation:** never use one customer's data to train or evaluate another customer's moderation model without explicit consent.

### Safety decision model

Every automated decision should produce:

```text
decision_id
tenant_id
rule_version
signal_categories
confidence_band
action
review_required
expires_at
appeal_state
```

Never store raw sensitive content in audit logs. Store references, hashes, policy version, and the minimum decision metadata needed for review.

### Human governance

- Assign an owner for policy, security, privacy, and abuse response.
- Review false positives and false negatives on a scheduled cadence.
- Version policy rules and models.
- Require two-person approval for permanent tenant suspension or data deletion.
- Preserve export access where legally and contractually required.
- Provide a customer-facing explanation for restrictions.

## 5. Database and tenant security

- Put `tenant_id` on every business table.
- Enable RLS on every public table.
- Add explicit grants and policies in the mandated order.
- Require active tenant status for anonymous published reads.
- Repeat tenant and role checks in `WITH CHECK`.
- Revoke direct authenticated inserts into `audit_events`.
- Generate audit events only through trusted triggers or controlled procedures.
- Keep scan and audit data append-only.
- Hash-chain audit rows with deterministic canonical serialization.

**Acceptance artifacts:**

```text
artifacts/s4-rls.json
artifacts/s5-roles.json
artifacts/s-audit-chain.json
```

## 6. Storage and media security

- Keep buckets private.
- Always issue short-lived signed URLs.
- Do not return permanent public URLs for protected media.
- Generate object keys from tenant ID, asset kind, UUID, and validated extension.
- Enforce extension, MIME, magic-byte, size, and SHA-256 checks.
- Delete the object and database row in a verified workflow.
- Scan uploads before publication and isolate processing workers from serving infrastructure.

## 7. Licensing and anti-resale controls

- Verify signed manifests locally with the embedded public key.
- Bind the licence to customer ID, domain, Cloudflare project, Supabase project, and release hash.
- Reject incomplete fingerprints with `400 incomplete_fingerprint`.
- Return `409 duplicate_activation` for a second active fingerprint.
- Keep guest playback available during vendor outages using a signed 30-day grace token.
- Make expiry control update entitlement, not ordinary runtime availability.
- On revocation, make the dashboard read-only while preserving export access for the defined grace period.
- Keep signing keys and vendor administration outside customer bundles.

## 8. Rate limits

Verify these budgets against staging:

| Operation | Budget | Key |
|---|---:|---|
| Licence activation | 5/hour | fingerprint + trusted IP |
| Licence heartbeat | 12/hour | tenant |
| Presigned upload | 60/hour | authenticated user |
| Public scan resolution | 120/minute | trusted IP |
| Sign-in | 10/15 minutes | normalized email + trusted IP |

Return `429` with `Retry-After`, audit activation abuse, and fail closed for mutations when the limiter backend is unavailable.

## 9. Supply-chain and client isolation

- Prefer self-hosted AR libraries.
- Otherwise pin exact versions and verify SRI hashes in CI.
- Allow only approved browser `VITE_*` variables.
- Scan full Git history with gitleaks.
- Run dependency vulnerability scanning and `npm audit`/Bun-equivalent checks.
- Verify no private signing key, service role, worker module, or issuer route is reachable from the client profile.

## 10. CI/CD and evidence

Required gates:

```text
bun install --frozen-lockfile
bun run typecheck
bun run lint
bun test
bun run build:admin
bun run build:client
bun run build:selfhost
bun run test:e2e
bun run verify:rls
bun run verify:audit-chain

```

CI must:

- use staging, never production, for load tests;
- preserve raw output beside parsed artifacts;
- fail when required checks fail;
- explicitly report `NOT_VERIFIED` when credentials or tools are unavailable;
- publish immutable build metadata and rollback references;
- require manual approval for production.

Required evidence includes:

## 11. Staging and production verification

Before production:

- deploy all profiles to isolated staging targets;
- test login, MFA enrollment, role changes, tenant crossover, uploads, QR playback, camera denial, licence lifecycle, revocation, grace mode, backups, restore, and rollback;
- test on supported Android and iPhone devices;
- run k6, autocannon, database explain plans, R2 throughput, cold-start, heap, and CPU profiling tests;
- verify alerts, retention, incident response, and key rotation;
- review ethical-use decisions and appeal workflows with test fixtures.

## 12. Definition of done

The project may be called production-ready only when:

- no critical or high-severity findings remain;
- all required automated gates pass;
- every claimed security phase has external evidence;
- missing staging evidence is explicitly listed as `NOT_VERIFIED`;
- Argon2id migration and bcrypt compatibility tests pass;
- ethical-use safeguards are documented, versioned, monitored, and appealable;
- deployment, rollback, backup, restore, and incident procedures are exercised;
- a responsible owner signs off on security, privacy, operations, and customer handover.
